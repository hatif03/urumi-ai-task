# Deploying on a VPS (k3s)

The same chart that runs on k3d runs on a single-node k3s VPS. Nothing in `deploy/helm/urumi/templates` changes; the differences are values and secrets. Decision record: [ADR 0018](adr/0018-tls-and-vps-strategy.md), [ADR 0005](adr/0005-one-helm-chart-two-value-files.md).

> **Status of this document.** The chart renders and lints with `values-prod.yaml`, and the TLS wiring (cert-manager, certificate secrets, `https` cookies and OAuth issuer) was rehearsed on the local k3d cluster with a private CA (`docs/log.md`, 2026-10-20). A run on a real VPS with a public domain and Let's Encrypt has **not** been done from this repository; the steps below are the checklist for that run. If you do it, record the date and what differed in `docs/log.md`.

## What you need

| Item | Notes |
| --- | --- |
| A VPS | 4 vCPU, 8 GiB RAM, 60 GiB disk is comfortable for the platform plus three stores. 2 vCPU / 4 GiB runs the platform and one store. Ubuntu 22.04 or 24.04, root access. |
| A domain | `dashboard.<domain>`, `shop.<domain>` and the wildcard `*.stores.<domain>` as A records to the VPS address. |
| Ports | 80 and 443 reachable from the internet (Let's Encrypt HTTP-01 uses 80). |
| A container registry | The six images (gateway, dashboard, provisioner, woocommerce-mcp, utility-mcp, policy-mcp). GitHub Container Registry works. |
| An LLM key (optional) | Without it chat answers 503 and everything else works. |

## Steps

1. **Build and push the images with a version tag** from your workstation (the build context is the repository root):
   ```sh
   export REGISTRY=ghcr.io/<you> TAG=1.0.0
   for n in gateway dashboard provisioner woocommerce-mcp utility-mcp policy-mcp; do
     docker build -f apps/$n/Dockerfile -t $REGISTRY/urumi-$n:$TAG . && docker push $REGISTRY/urumi-$n:$TAG
   done
   ```
2. **Copy the repository to the VPS** (or `git clone` it there) and run the bootstrap as root:
   ```sh
   DOMAIN=example.com EMAIL=ops@example.com REGISTRY=$REGISTRY TAG=$TAG bash scripts/vps-bootstrap.sh
   ```
   It installs k3s with Traefik disabled, Helm, ingress-nginx and cert-manager; generates every secret into `/root/urumi-secrets.env` (mode 600) and creates the Kubernetes Secrets from it; runs `helm upgrade --install --atomic --wait` with `values-prod.yaml` and the overrides below; then `helm test`. Private registries need an image pull secret: create it in `platform`, `store` and add `imagePullSecrets` through `HELM_EXTRA` or `provisioner.storeValues`.
3. **Open the dashboard** at `https://dashboard.<domain>`, user `ada`, the password printed at the end (and in the secrets file as `ADMIN_PASSWORD`). Create a member, issue keys, add an LLM key if you want chat.
4. **Prove it end to end** from your workstation: `ENTRY=https://dashboard.<domain> DASHBOARD_HOST=dashboard.<domain> SHOP_HOST=shop.<domain> ADMIN_PASSWORD=... bun scripts/e2e.ts` (set `STORES=1` for the multi-store bonus; stores appear at `https://<slug>.stores.<domain>`).

## What changes between local and the VPS

| Concern | Local (`values-local.yaml`) | VPS (`values-prod.yaml` + bootstrap overrides) |
| --- | --- | --- |
| Cluster | k3d, one server container, ports 80:80 | k3s on the VPS, Traefik disabled, servicelb publishes 80/443 |
| Domains | `shop.local`, `dashboard.local` in the hosts file; stores at `<slug>.shop.localhost` (resolves to loopback in browsers and curl, no entry per store) | `shop.<domain>`, `dashboard.<domain>`, stores at `<slug>.stores.<domain>` (wildcard A record) |
| TLS | off; cookies not `Secure` | `ingress.tls.enabled`, cert-manager `ClusterIssuer` (Let's Encrypt HTTP-01), a certificate per host, `COOKIE_SECURE=true`, OAuth issuer `https://dashboard.<domain>` |
| `publicBaseUrl` | `http://dashboard.local` | `https://dashboard.<domain>` (the OAuth issuer and token audience; keep it stable) |
| Images | `urumi-*:local`, `pullPolicy: Never`, imported with `k3d image import` | `<registry>/urumi-*:<version>`, `IfNotPresent` |
| Storage | `local-path`, 5 GiB claims | `local-path` on the VPS disk (or a CSI class you install), 10 GiB claims; `helm.sh/resource-policy: keep` on the platform's own claims |
| Store defaults | `storesScheme: http` | `storesScheme: https`, same quotas |
| Replicas and limits | 2 gateway / dashboard / MCP, HPA max 2, small limits | same replicas, HPA max 4, larger WordPress and gateway limits, provisioner 2 replicas |
| Secrets | generated by `dev-up.sh` into `deploy/secrets/generated.env` (gitignored) | generated by `vps-bootstrap.sh` into `/root/urumi-secrets.env`; the same Secret names; never in values files or the repository |
| Hosted MCP registries | `urumi-`, `ghcr.io/` | your registry prefix only |

The complete override list is the `helm upgrade` block in `scripts/vps-bootstrap.sh`.

## Local rehearsal of the TLS path

Run the production wiring on k3d with a private CA, which proves the Ingress `tls:` blocks, the cert-manager annotation, secure cookies and the https issuer without a domain:

```sh
helm upgrade --install cert-manager cert-manager --repo https://charts.jetstack.io -n cert-manager --create-namespace --set crds.enabled=true --wait
helm upgrade urumi deploy/helm/urumi -n platform -f deploy/helm/urumi/values-local.yaml \
  --set certManager.enabled=true --set certManager.selfSigned=true --set certManager.issuerName=urumi-local \
  --set ingress.tls.enabled=true --set ingress.tls.clusterIssuer=urumi-local \
  --set publicBaseUrl=https://dashboard.local --set wordpress.url=https://shop.local
kubectl get certificate -A
curl -k --resolve dashboard.local:443:127.0.0.1 https://dashboard.local/.well-known/oauth-protected-resource
```
(`k3d` publishes port 80 only; add `-p 443:443@loadbalancer` to `deploy/k3d/cluster.yaml` for the 443 request, or use `kubectl port-forward -n ingress-nginx svc/ingress-nginx-controller 8443:443`.)

## Hardening checklist for the VPS

- Firewall: allow 22, 80, 443 only; k3s API (6443) closed to the internet (`ufw default deny incoming`).
- SSH keys only, no password login.
- Put `/root/urumi-secrets.env` in a password manager; it is the only copy of the key that decrypts stored upstream credentials.
- `kubectl -n platform get networkpolicy` should list the policies from the chart; k3s enforces them with its built-in network policy controller.
- Upgrades and rollbacks: [runbook](runbook-upgrade-rollback.md).
